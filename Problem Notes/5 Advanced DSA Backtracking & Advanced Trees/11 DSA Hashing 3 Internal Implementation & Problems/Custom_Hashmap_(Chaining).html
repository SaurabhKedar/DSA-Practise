Custom HashMap (Chaining)

The key concepts in this problem are hashing, separate chaining using linked lists, and rehashing when the load factor exceeds 2.0.

We will implement the HashMap from scratch without using Java's built-in HashMap, Dictionary, or similar classes.

1. Problem understanding

We need to create a class CustomHashMap that stores integer key–value pairs and supports four operations.

OperationExpected behavior
put(key, value)Insert a new pair or update an existing key
get(key)Return the value, or -1 if absent
remove(key)Delete the key and return its old value, or -1 if absent
size()Return the number of stored key–value pairs

The initial number of buckets is 4. The bucket index is:

\[\text{index} = |\text{key}| \bmod \text{bucketCount}\]

When the load factor exceeds 2.0, double the number of buckets and reinsert all existing entries.

\[\lambda = \frac{\text{number of elements}}{\text{number of buckets}}\]

What is chaining?

Different keys can produce the same bucket index. Instead of overwriting an entry, we store all entries assigned to that bucket in a linked list.

Example: bucket count = 4

Bucket 0null Bucket 1null Bucket 2(2, 100) → (6, 200) → (10, 300) → null Bucket 3null

Keys 2, 6, and 10 all map to bucket 2 because their remainders when divided by 4 are identical.

2. Brute-force approach

The simplest possible approach is to store all key–value pairs in a linked list and search through the entire list for every operation.

  • put: traverse the list to check whether the key exists; update it or append a new node.
  • get: scan all nodes until the key is found.
  • remove: scan the list, unlink the matching node, and return its value.
  • size: maintain a counter.
Why not use this as the final solution? It takes \(O(N)\) time for lookups and updates, where \(N\) is the number of stored pairs. The problem specifically requires hashing with chaining, so the bucket array is necessary to make operations faster on average.

3. Optimized approach — Hashing + Separate Chaining

Intuition

Instead of searching every key, calculate its bucket index and search only the linked list in that bucket.

We need three components:

  1. Bucket array: An array of linked-list heads, initially of length 4.
  2. Node: Stores a key, value, and pointer to the next node.
  3. Size counter: Tracks how many unique key–value pairs currently exist.

Algorithm step by step

put(key, value)

  1. Calculate the bucket index.
  2. Traverse the linked list in that bucket.
  3. If the key exists, update its value and return.
  4. Otherwise, insert a new node at the head of the list and increment size.
  5. If size / bucketCount > 2.0, rehash.

get(key)

  1. Calculate the bucket index.
  2. Search only that bucket's linked list.
  3. Return the matching value or -1.

remove(key)

  1. Calculate the bucket index.
  2. Search the linked list while keeping track of the previous node.
  3. If found, unlink the node, decrement size, and return its previous value.
  4. Otherwise, return -1.

rehash()

  1. Save the old bucket array.
  2. Create a new array with twice as many buckets.
  3. Recalculate the bucket index of every existing key.
  4. Insert every existing entry into its new bucket.

Rehashing must not change the number of stored entries.

4. Complete Java solution

The following code preserves the required CustomHashMap class name and method signatures.

class CustomHashMap {

    // A node in a bucket's linked list.
    private static class Node {
        int key;
        int value;
        Node next;

        Node(int key, int value) {
            this.key = key;
            this.value = value;
            this.next = null;
        }
    }

    private Node[] buckets;
    private int size;

    private static final int INITIAL_CAPACITY = 4;
    private static final double MAX_LOAD_FACTOR = 2.0;

    public CustomHashMap() {
        buckets = new Node[INITIAL_CAPACITY];
        size = 0;
    }

    // Calculate the bucket index for a key.
    private int getIndex(int key) {
        return Math.abs(key) % buckets.length;
    }

    public void put(int key, int value) {
        int index = getIndex(key);
        Node current = buckets[index];

        // Update an existing entry without changing the size.
        while (current != null) {
            if (current.key == key) {
                current.value = value;
                return;
            }
            current = current.next;
        }

        // Insert a new entry at the head of this bucket's list.
        Node newNode = new Node(key, value);
        newNode.next = buckets[index];
        buckets[index] = newNode;
        size++;

        // Rehash only after adding a new key and exceeding the limit.
        double loadFactor = (double) size / buckets.length;
        if (loadFactor > MAX_LOAD_FACTOR) {
            rehash();
        }
    }

    public int get(int key) {
        int index = getIndex(key);
        Node current = buckets[index];

        // Search only the linked list in the calculated bucket.
        while (current != null) {
            if (current.key == key) {
                return current.value;
            }
            current = current.next;
        }

        return -1; // The key was not found.
    }

    public int remove(int key) {
        int index = getIndex(key);
        Node current = buckets[index];
        Node previous = null;

        while (current != null) {
            if (current.key == key) {
                int oldValue = current.value;

                // Removing the first node requires updating the bucket head.
                if (previous == null) {
                    buckets[index] = current.next;
                } else {
                    // Removing a middle or last node links around it.
                    previous.next = current.next;
                }

                size--;
                return oldValue;
            }

            previous = current;
            current = current.next;
        }

        return -1; // The key was not found.
    }

    public int size() {
        return size;
    }

    // Double the bucket count and redistribute every existing entry.
    private void rehash() {
        Node[] oldBuckets = buckets;

        // The new length is twice the old capacity.
        buckets = new Node[oldBuckets.length * 2];

        // Reinsert entries using indices calculated for the new capacity.
        for (Node head : oldBuckets) {
            Node current = head;
            while (current != null) {
                int index = getIndex(current.key);
                Node newNode = new Node(current.key, current.value);

                // Add each copied entry at the head of its new bucket.
                newNode.next = buckets[index];
                buckets[index] = newNode;
                current = current.next;
            }
        }

        // Do not change size during rehashing.
    }
}

Important implementation details

  • Updating an existing key: We return immediately without incrementing size or unnecessarily rehashing.
  • Removing a node: We handle the bucket head separately because it has no previous node.
  • Rehashing: We create new nodes so the old linked lists remain untouched during traversal.
  • Negative keys: Math.abs(key) works under the given constraint \(|key| \leq 10^9\), which excludes Integer.MIN_VALUE.
  • Load factor: Rehash only when it is strictly greater than 2.0, not equal to it.

When does rehashing happen?

With four buckets, the maximum permitted number of elements before rehashing is eight.

New element countLoad factorAction
71.75No rehash
82.00No rehash
92.25Double bucket count from 4 to 8

After the ninth unique insertion, all existing entries are redistributed using % 8 instead of % 4. Updating an existing key does not trigger rehashing because the element count does not change.

6. Complexity analysis

Let \(N\) be the number of stored key–value pairs and \(B\) the number of buckets.

OperationAverage timeWorst-case time
put\(O(1)\) amortized\(O(N)\)
get\(O(1)\)\(O(N)\)
remove\(O(1)\)\(O(N)\)
size\(O(1)\)\(O(1)\)
rehash\(O(N+B)\)\(O(N+B)\)

Why is the average time \(O(1)\)?

The load factor is kept at or below 2.0 after each insertion, so the average number of entries per bucket stays bounded. Assuming keys are distributed reasonably across buckets, each operation examines only a small linked list on average.

Why is the worst case \(O(N)\)?

If every key maps to the same bucket, that bucket's linked list can contain all \(N\) entries. Searching, updating, or removing a key may then require traversing the entire list.

Rehashing is \(O(N+B)\) because we must visit the old buckets and redistribute every entry. Since it occurs only occasionally as the table grows, insertion is \(O(1)\) amortized under ordinary hashing assumptions.

Space complexity: \(O(B+N)\) total space for the bucket array and linked-list nodes. Auxiliary space during rehashing is \(O(N+B)\) because the implementation temporarily retains the old array and creates new nodes in the new array.

7. Edge cases

CaseExpected behavior
Get a missing keyReturn -1

Multiple keys collideStore them in the same linked list
Remove the bucket's first nodeUpdate the bucket head
Remove a middle or last nodeLink the previous node to the next node

Negative keyCompute the index using its absolute value
Large positive or negative keyCorrectly calculate the bucket index within the stated constraints
Remove all entriesSize becomes zero; buckets remain allocated

One important detail: -1 is the required missing-key result. The API therefore uses -1 as the not-found indicator, even though negative values are valid values.

9. Interview preparation notes

Key concepts to remember

  • Separate chaining: Each bucket contains a linked list of entries that collide.
  • Load factor: Measures how full the hash table is relative to its bucket count.
  • Rehashing: Expands the bucket array and redistributes entries using the new capacity.
  • Amortized complexity: Occasional expensive rehashes are spread across many insertions.
  • Size tracking: Increase only on a new key; decrease only on a successful removal.

Common mistakes

  1. Incrementing size when updating an existing key.
  2. Forgetting to handle removal of the head node.
  3. Rehashing when the load factor is exactly 2.0.
  4. Using the old bucket count to calculate indices after rehashing.
  5. Resetting size incorrectly or incrementing it during rehashing.
  6. Using Math.abs() without considering the minimum integer edge case in problems with unrestricted integer keys. The given constraints exclude that value.

Likely interviewer follow-up questions

Q1. Why use chaining instead of open addressing?

Chaining allows multiple entries to occupy the same bucket through a linked list. Deletion is straightforward, and the table can hold more entries than buckets.

Q2. Why double the bucket count?

Doubling reduces the load factor significantly and avoids resizing too frequently. It is a common resizing strategy for hash tables.

Q3. What if every key maps to the same bucket?

Operations may degrade to \(O(N)\). A better hash distribution helps avoid this, although chaining still handles collisions correctly.

Q4. Why is insertion amortized \(O(1)\) rather than always \(O(1)\)?

Most insertions take constant time on average, but an insertion that triggers rehashing must redistribute all existing entries. Over many insertions, the occasional resizing cost averages out.

10. Final recommendation

For this problem, implement the bucket array + singly linked list + load-factor-based rehashing solution above. It directly satisfies the requirements and is suitable for an interview.
